# Evals

Measures how well the deployed RAG system retrieves the right documents, refuses questions it
cannot answer, and how fast and expensive it is. It calls the live `POST /ask` API.

## Question format

`evals/questions.jsonl`, one JSON object per line:

```json
{"id": "q01", "question": "How can I ...?", "expected_sources": ["docs/path-params.md"], "answerable": true, "difficulty": "direct"}
```

| Field | Meaning |
|---|---|
| `id` | Unique id (`q01` ...). Used by `--ids` and in reports. |
| `question` | What a developer would type (max 500 chars, the API limit). |
| `expected_sources` | Doc keys that contain the answer, e.g. `docs/cors.md`. Two entries for questions that need two docs. `[]` when `answerable` is false. |
| `answerable` | `false` for questions the docs cannot answer; the system should refuse these. |
| `difficulty` | Optional: `direct`, `understanding`, `multi` or `unanswerable`. Metrics are also broken down by it. |

The current set has **40 questions**: 32 answerable (20 direct, 8 understanding, 4 multi-doc)
and 8 unanswerable (ids `q33`-`q35` are off-topic general knowledge, `q36`-`q40` are near-misses
that sound like FastAPI but are not covered by the tutorial docs: JWT auth, WebSockets, Docker,
rate limiting, `.env` settings).

### How the set was made

Generated by an AI assistant from the files in `sample-docs/`, then reviewed by a human:

- Questions are phrased the way a developer would ask, with synonyms and the goal described, not
  the docs' own wording or headings (so retrieval can't win by keyword overlap alone).
- No doc is the expected source for more than 2 questions, and the answerable questions are
  spread over as many docs as possible.
- For every answerable question the assistant located the passage containing the answer in the
  expected doc. For every near-miss it searched `sample-docs/` to confirm the topic is absent
  (JWT, WebSocket, Docker, rate limiting and `BaseSettings` / `.env` appear nowhere).
- The unit tests check the file mechanically: valid format, expected docs exist, the 2-per-doc cap.

The wording and answers should still be spot-checked by a human; fix a question or its
`expected_sources` whenever you find one that is wrong.

## Running

Install nothing extra: the runner only uses the Python standard library.

```powershell
$url = terraform -chdir=infra\envs\demo output -raw ask_url

# 3-question smoke run (does not touch RESULTS.md)
.\.venv\Scripts\python.exe evals\run_evals.py --url $url --limit 3

# full run
.\.venv\Scripts\python.exe evals\run_evals.py --url $url
```

Useful flags:

| Flag | Purpose |
|---|---|
| `--pause 3` | Seconds between questions (default 3, for Gemini free-tier limits). |
| `--skip-sources docs/a.md,docs/b.md` | Skip every question whose `expected_sources` include one of these docs. Skipped ids are listed in the summary and the results JSON, and the `RESULTS.md` row is marked `PARTIAL`. Use it while some docs are not indexed yet. |
| `--limit N` / `--ids q01,q05` | Run a subset. Smoke runs don't append to `RESULTS.md` unless you add `--append-row`. |
| `--retries 2 --retry-pause 10` | Retry 429 / 503 / network errors. |
| `--embedding-model`, `--chunk-size`, `--chunk-overlap`, `--top-k`, `--threshold` | The API doesn't report its server-side settings, so pass the deployed values; they are only **recorded** in the results (defaults match the current deployment). |

Only run the full set once every doc is indexed (or use `--skip-sources`); questions about
missing docs otherwise show up as retrieval failures.

## Reading the output

- **hit@k**: share of answerable questions where a source from `expected_sources` appears in the
  first k returned sources. **MRR**: mean of 1/rank of the first such source (0 when absent).
  For multi-doc questions the rank is that of the first expected doc found; the report also shows
  how many of the expected docs were found in the top 5.
- **Refusals**: a *correct refusal* is an unanswerable question answered with "I don't know".
  A *wrong refusal* is an answerable question refused. The report separates refusals made by the
  **threshold** (the Lambda refuses before calling the model) from refusals made by the **LLM**.
  Right now the threshold (0.6) never triggers, so refusals come from the LLM.
- **Threshold sweep**: for each threshold from 0.300 to 0.600 (step 0.025), how many unanswerable
  questions would be refused before the LLM (top distance above the threshold) and how many
  answerable ones would be wrongly refused. The suggested threshold has zero wrong refusals and
  the most correct ones (ties go to the higher value). With about 40 questions this is a
  starting point, so keep a safety margin; to apply it, set `distance_threshold` in Terraform.
- **Latency** is the `latency_ms` reported by the API (server side); client round-trip times are
  in the JSON.

Outputs: the terminal summary, `evals/results/<timestamp>.json` (every question's status,
answer, sources, distances, tokens; git-ignored) and one row appended to `evals/RESULTS.md`.

## Collections

The index holds several document collections (a sub-folder under `docs/` is a collection;
files directly under `docs/` belong to `fastapi`). Evaluate each collection with its own
question file and the matching `--collection` flag, so retrieval is restricted to it:

```powershell
$url = terraform -chdir=infra\envs\demo output -raw ask_url
.\.venv\Scripts\python.exe evalsun_evals.py --url $url --collection fastapi
.\.venv\Scripts\python.exe evalsun_evals.py --url $url --questions evals\questions_business.jsonl --collection business
```

`questions_business.jsonl` has 10 questions (8 answerable, one needing two documents, 1 off-topic,
1 near-miss about gift wrapping, which the fictional company's documents do not cover). Some
answers live in the PDFs. Cost per 1,000 questions can be recomputed from any result file with
`python scripts/estimate_cost.py evals/results/<run>.json`.
